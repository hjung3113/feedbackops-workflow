# Live TUI is a separate execution mode with adapter-owned session control

Status: accepted

`execution_mode` is a separate axis from the existing permission `mode`: `headless` remains the default for every adapter except `orca`, whose CLI-level default is `live-tui` when `--execution-mode` is omitted, while phase 1 admits `live-tui` only for an implementation seat with write permission. Runtime members own command policy and emit a shell-free launch spec (`argv[]`, `env`, and `prompt_delivery`); transport adapters own session lifecycle and never interpret runtime-specific flags. This keeps the existing headless runner/watchdog path unchanged and prevents a missing live capability from silently falling back to headless.

## Durable live contract

- D1: launch acknowledgement and liveness evidence is `.review/ISSUE-N-launch.*/LIVE.json`. It records ready and prompt-start activity only, never workflow completion.
- D2: `live-session-supervisor.sh` owns the adapter-neutral sequence `wait-ready -> baseline read -> send -> activity`; its settled and canonical-artifact gate functions cover the later `settled -> artifact-gate` phase.
- D3: the launch spec is argv-shaped. Orca's later adapter implementation may join each token with `printf %q` for its required single command string; naive concatenation is not a valid transport.
- D4: Codex live argv explicitly carries `--ask-for-approval never`.
- D5: selection is only `dispatch-core.sh --execution-mode headless|live-tui` in this phase. No workflow-config or model-allocation key selects it. As of 2026-08-24, the CLI-level default is `live-tui` for the `orca` adapter only when `--execution-mode` is omitted; an explicit `--execution-mode` remains authoritative, and every other adapter still defaults to `headless`.
- D6: transport receipt schema v4 carries `execution_mode`, structured `handles`, and `launch_spec_sha256`. `external_handle` is optional; `runner` is conditional and required only for `execution_mode=headless`. Live receipts do not perform runner hash checks.
- D7: settled classification is normalized to `settled|working|blocked|stale|terminal`. Orca requires post-send activity plus `tui-idle`; Herdr maps its native states directly; cmux can claim settled only with a help-proven agent-state query, otherwise canonical artifact polling remains authoritative and screen matches are diagnostic.
- D8: phase 1 emits `prompt_delivery: transport` for every runtime. `initial-argv` remains an enum slot but is not admitted.
- D9: live partial-work stashing is limited to adapter-reported abnormal termination or a transport disconnect after activity and before a fresh canonical artifact. Blocked and settled-without-artifact are contract failures, not stash triggers.
- D10: Herdr remains a future write-capable transport implementation; T1 defines the shared seam and does not add an adapter-specific Herdr path or exclude it from the eventual write-dispatch set.
- D11: live timeouts are `LIVE_WAIT_READY_TIMEOUT_MS`, `LIVE_SEND_ACTIVITY_TIMEOUT_MS`, `LIVE_WAIT_SETTLED_TIMEOUT_MS`, and `LIVE_SESSION_TIMEOUT_MS`, defaulting to watchdog-scale 240000, 180000, 180000, and 3600000 milliseconds respectively.

The semantic adapter capabilities are `session.live.launch`, `session.ready.wait`, `session.input.send`, `session.output.read`, `session.activity.observe`, `session.state.wait`, `session.interrupt`, and `session.close`. A transport must prove the complete set before live admission; headless availability is reported separately.

## T5 decision gate: does `execution_mode` default flip? (2026-08-22)

**Decision: no default flip. `execution_mode` stays explicit-opt-in `--execution-mode live-tui` (D5), per-adapter, not global, until each adapter has passed its own real-binary verification pass.**

Rationale, by adapter:

- **cmux**: archived (#208, see HANDOFF.md and `toolkit/STATUS.md`). Real cmux 0.64.x lacks the subcommands the T4 adapter assumed; its live capability already fails closed at the capability-probe stage. Not eligible for any default until #208's rewrite lands and is itself real-binary verified. Out of scope for further work until orca/herdr are stable (see the archive note).

- **orca**: partially real-binary verified 2026-08-22 (orca 1.4.188, from inside a live Orca terminal). `capabilities --probe-live`, `launch-live`, `wait-ready`, `read`, `wait-settled`, `send`, and stale-handle detection on `wait-ready`/`wait-settled`/`send` (#206's fix) all behaved correctly against the real binary. That same pass found `read` never inspected the closed-terminal `status:"exited"` field real Orca returns on a zero-exit response, silently returning `{"output":"","cursor":"0"}` instead of a stale signal — filed as #210, and **#210 landed 2026-08-23** (PR #213, merged, smoke-verified with a regression case covering the post-reacquire-still-exited branch too). **#210's fix re-verified against the real orca binary 2026-08-24**: created a real terminal (orca 1.4.188), let it exit, confirmed the exact bug shape live (`terminal read` returns exit 0, `ok:true`, `result.terminal.status:"exited"`, `tail:[]`), then drove the adapter's `read` subcommand directly against that real closed handle — it now fails closed (`ERROR: live_read_failed: terminal read failed`, exit 1) instead of the old silent empty-success. No open defects remain against orca's live adapter.

- **herdr**: real-binary verified 2026-08-22 (herdr 0.8.0, from inside a live Herdr session, real omp/glm-5.3 agent). `capabilities --probe-live` correctly stays headless-only (fail-closed). `read`, `send` (happy path), `inspect`, and stale-handle detection on `read`/`send`/`inspect` after a real workspace close all behaved correctly — no #210-equivalent silent-success bug found here. This pass found two real-binary defects: **#211** — `parse_agent_state` read the wrong JSON field (`.result.agent.status` instead of real herdr's `.result.agent.agent_status`), so `wait_ready` and `wait_settled` always failed even against a genuinely idle agent — **landed 2026-08-23** (PR #214, merged, smoke-verified, not yet re-verified against the real binary). **#211's fix re-verified against the real herdr binary 2026-08-24**: started a real omp agent (herdr 0.8.0, `HERDR_ENV=1` live session), drove the adapter's `wait-ready` and `wait-settled` subcommands directly against it — `wait-ready` returned exit 0 on genuinely `idle`, `wait-settled` correctly returned `{"state":"settled"}` for `idle`/`done`. A genuinely `working` mid-turn state was captured directly from `herdr agent get` (`agent_status:"working"`) and fed through `parse_agent_state`, which classified it correctly (no `*_state_invalid`) — the field-name fix holds for all three lifecycle states against the real binary. **#212 is implemented**: its production-shaped fresh/untrusted-worktree characterization now crosses `agent start`, emits the exact runtime line `> You are in <dir>`, parses structured `agent start`/`agent get` errors from either stream, and correlates the timeout path with `agent_not_found`. Herdr 0.8.0 produces that `timeout`/`agent_not_found` pair, so live remains unavailable while headless stays intact; `agent_not_ready` followed by retained `agent_status:"blocked"` is the fixed v0.8.2+ contract reserved for later real-binary verification and is not admitted by #212. False-ready, malformed, mismatched, and non-blocked results fail closed, and workspace close reaps the probe agent and sentinel. **#215 landed 2026-08-23**: for codex launches the trust prompt is now prevented upstream — `launch_live` pre-seeds codex's own per-directory trust store (`[projects."<cwd>"] trust_level = "trusted"` in `$CODEX_HOME/config.toml`) before `agent start`, so the codex trust screen never renders; smoke coverage asserts the TOML-safe merge, idempotency, and that a sentinel codex never hits the trust screen. **#215/#218's codex trust pre-seed re-verified against a real codex binary 2026-08-24** (codex-cli 0.148.0, real ChatGPT-plan auth, from inside a live Herdr session, `HERDR_ENV=1`): baseline reproduced first — a genuinely never-trusted fresh git worktree, launched with the exact production live-launch argv (`codex --sandbox workspace-write --cd <cwd> --ask-for-approval never`), hit the real "Do you trust the contents of this directory?" TUI prompt and blocked waiting for input, confirming the bug shape still exists in this codex version. `toolkit/scripts/runtimes/codex.sh pre-launch --cwd <cwd>` (the real production entrypoint, not a mock) was then run directly against that same path, writing the exact-path `[projects."<cwd>"] trust_level = "trusted"` entry into `config.toml`. Relaunching real codex with the identical argv against the same worktree reached the ready prompt directly — the trust screen never rendered. #212's production-shaped implementation is now present, but v0.8.2+ real-binary verification remains outstanding. #215/#218's codex live-launch path no longer depends on the generic trust probe.

**Net**: **orca now has a complete real-binary pass with zero open defects** (2026-08-22 initial pass + #210 fix re-verified 2026-08-24) — first adapter to clear this bar; the T5 default-flip decision for orca specifically can be revisited as a follow-up now that this condition is met (still requires an explicit decision, not automatic). Herdr's #211 fix and #215/#218's codex trust pre-seed are now both real-binary re-verified (2026-08-24), but herdr as a whole remains ineligible for a default flip: #212's implementation is present, while its v0.8.2+ real-binary verification remains outstanding. cmux still needs #208 first. Do not flip the global default or move any adapter's default independently of this gate — this record is the authority per D5, supersedes prose in stale handoff files.

### 2026-08-24 — orca-specific default flip decision

The follow-up decision is now made: when `--execution-mode` is omitted, `execution_mode` defaults to `live-tui` for the `orca` adapter only. All other adapters remain `headless` by default, and explicitly passing `--execution-mode headless` or `--execution-mode live-tui` always overrides the adapter-based default. This implements the “can be revisited as a follow-up” note above; it remains a CLI argument-parsing default, not a workflow-config or model-allocation key.
